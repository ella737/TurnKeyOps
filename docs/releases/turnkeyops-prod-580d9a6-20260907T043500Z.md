## Release notes

This release moves TurnKeyOps from browser/server-local operational state to
tenant-partitioned production workflows and adds enforceable delivery gates.

| Area | Included change |
| --- | --- |
| Quote intake | Durable tenant-resolved quote requests and private attachment storage, with idempotent public intake and safe failure states |
| Estimates | Server-owned totals, revisions, delivery, customer decisions, expiration, and immutable history |
| Billing | Durable invoices, payment reconciliation, webhook replay protection, reminders, and service-owned job-release rules |
| Jobs | Durable jobs, schedules, materials, notes, status history, conflict checks, and optimistic concurrency |
| Authorization | Explicit roles/permissions, service-layer tenant enforcement, negative-path tests, and fail-closed sessions |
| Tenant configuration | Durable content, contact access, billing, estimate, brand, and operational settings with version checks |
| Bob | Tenant-scoped conversation/action persistence, approval policy, idempotency, and audit history |
| Security | Tracked PII and production diagnostic-auth surfaces removed; secret/PII scanning is a release gate |
| Integrations | Production identity and communication configuration is validated; billing remains fail-closed until explicitly configured and enabled |
| Admin experience | Demo calendar, weather, team, invoice, and other local success states were removed or replaced with live API states |
| Delivery controls | GitHub Actions quality, zero-retry browser, immutable-package, UAT, approval, smoke, and evidence gates are authoritative; Azure DevOps deploy definitions are retired |

## Data and storage migration sequence

This release has no relational migrations or SQL scripts. The repository gate
confirmed that posture, and Azure Table/Blob behavior is covered by API and
emulator tests. The storage changes are additive and tenant partitioning is
part of every service contract.

For a fresh environment or controlled replay:

1. Stop customer-facing mutations and record the release SHA, storage account,
   UTC start, and operator.
2. Take the approved storage backup/export before changing data. Do not copy
   local `.svelte-kit`, Azurite, demo, or untracked JSON into production.
3. Deploy the API artifact so required Azure tables can be created by the
   configured repository layer. Run the idempotent authorization startup seed
   for role definitions and permission mappings.
4. Import and read back tenant settings in this order: brand/public content,
   estimate defaults, billing posture, operational settings, then contact
   access grants. Follow `api/docs/tenant-settings-migration.md` and preserve
   version values.
5. Import only business-approved records, in dependency order: customers and
   quote requests; quote attachments; estimates and line items; invoices and
   payment/webhook history; jobs, sites, and calendar events; Bob conversations
   and actions. Never import demo records as customer data.
6. Verify BDR and Think Pink counts and representative readbacks separately.
   Exercise cross-tenant denial before reopening writes.
7. Deploy the web artifact, run the repository smoke script, and attach the
   deployment JSON, hashes, readback results, and smoke log to the release.

Rollback is artifact-first. Application rollback must not delete or downgrade
Azure Tables or Blobs. If a candidate introduces a forward-incompatible data
write, disable the affected mutation, restore the pre-change storage backup to
an isolated account, validate it, and reconcile writes from the observation
window before switching traffic. A future relational migration is prohibited
from merging until forward and rollback jobs are added to the required gate.
